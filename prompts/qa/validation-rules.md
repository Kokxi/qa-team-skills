# 推理校验规则（Validation Rules）

## 定位

将各指令的"输出前自检"清单结构化，提供统一的校验规则。所有 `/qa-*` 指令的输出在返回用户前，必须逐条通过以下规则检查。

## 通用校验（所有指令必过）

| 规则 | 检查项 | 适用指令 |
|------|--------|---------|
| V001 | 输出格式是否与模板一致（缺少必填章节返回 **【格式校验失败】**） | 全部 |
| V002 | 是否有编造的数据（如有，替换为占位符"{{待确认}}"） | 全部 |
| V003 | 是否生成了「简明摘要（30秒速览）」 | 全部 |
| V004 | 记忆写入路径是否正确（`data/products/{module}/`） | 全部 |
| V005 | 是否已同步更新 `summary.json` | 全部（通过 /qa 调用时） |

## 指令特化校验

### /qa-prd

| 规则 | 检查项 |
|------|--------|
| P001 | 11 个评审维度是否全部检查（无问题则标注"未发现明显问题"） |
| P002 | 严重程度是否有判断依据（高=阻塞/安全、中=影响质量、低=改进建议） |
| P003 | "需澄清的问题"是否聚焦产品经理必须当场回答的关键决策点 |
| P004 | 是否包含评审结论（通过/不通过）？——不允许 |
| P005 | 是否给出「业务分层建议」？ |
| P006 | 是否已将完整报告导出为 Markdown 文档到 `docs/reviews/review-{module}-{YYYYMMDD}.md`？（用户明确拒绝导出时豁免） |

### /qa-case

| 规则 | 检查项 |
|------|--------|
| C001 | 每条用例是否标注了业务分层（核心层/体验层/增值层） |
| C002 | 每条用例是否标注了设计方法 |
| C003 | 每条用例的步骤是否以动词开头 |
| C004 | 是否每种测试类型至少覆盖 1 条用例 |
| C005 | 核心层用例是否覆盖了产品的最基本价值 |
| C006 | 业务分层与优先级是否合理匹配（核心层 P2-P3 为异常） |
| C007 | 是否从历史缺陷转化了补充用例？（如有历史数据） |
| C008 | 是否引用了规范库 checklist？（如有规范数据） |
| C009 | 涉及输入格式的场景（登录/注册等），是否覆盖了字符集、长度边界、空输入？ |
| C010 | 安全测试中是否包含信息泄露防护检查（错误提示是否通用化）？ |
| C011 | 是否执行了 latest.json 合并并更新了 summary.json？ |

### /qa-bug

| 规则 | 检查项 |
|------|--------|
| B001 | 是否先输出了质量评估（即使信息充分也简要标注"达标"） |
| B002 | 信息不足时是否拒绝给出根因分析？ |
| B003 | 根因分析的置信度是否合理标注 |
| B004 | 修复建议是否指向了具体的代码位置/方向 |
| B005 | 回归测试要点是否覆盖了关联功能和同类场景 |
| B006 | 批量模式中发现共性根因 → 是否检查了 standards.json 去重？ |

### /qa-report

| 规则 | 检查项 |
|------|--------|
| R001 | 报告类型是否与用户指定的匹配 |
| R002 | 所有数据是否有来源标注 |
| R003 | 缺失数据是否用 `-` 标注（不得编造数字） |
| R004 | 统计计算是否合理（修复率=已修复/总计） |

### /qa-team

| 规则 | 检查项 |
|------|--------|
| T001 | 是否正确匹配了用户需要的子能力 |
| T002 | 管理报告是否聚焦团队视角（不做个人绩效排名） |
| T003 | 趋势判断是否用 →（稳定）/ ↑（上升）/ ↓（下降） |
| T004 | 关注项是否仅标注显著变化（波动 >30%）或异常值 |
| T005 | 漏测复盘中的预防措施 → 是否检查了 standards.json 去重？ |

### /qa-agent

| 规则 | 检查项 |
|------|--------|
| A001 | 每条用例的设计方法是否已填写 |
| A002 | 16 个维度是否全部覆盖（不适用的标注"不适用"） |
| A003 | RAG 维度（14-16）是否根据 Agent 实际能力判断适用性 |
| A004 | 是否有编造的 Payload 或测试数据 |

### /qa-explore

| 规则 | 检查项 |
|------|--------|
| E001 | 探索任务卡是否含任务名称/目标/时间盒/3 个起点（起点不超过 3） |
| E002 | Session 笔记是否区分了"疑似 Bug"与"学习经验"（不混淆） |
| E003 | Debrief 报告是否汇总了发现+沉淀建议（而非简单的重复 Session 笔记） |
| E004 | 是否鼓励"走异常路径"（而非按预设用例执行） |

## 输出前自检流程

每次输出前按以下顺序检查：

```
Step 1: 通用校验（V001-V005）
  ├─ 全部通过 → 继续
  └─ 不通过 → 修正后重新检查

Step 2: 指令特化校验
  ├─ 找到当前指令对应的规则表
  ├─ 逐条检查
  ├─ 全部通过 → 输出
  └─ 不通过 → 标注具体规则编号和失败原因，修正后输出
```

## 格式校验失败

当输出缺少任一必填章节或字段时，返回：
```
【格式校验失败】
缺少：{{缺失的章节/字段}}
请修正后重新生成。
```

> 📄 **扩展格式**：如需输出「指令/原因/位置/建议」四字段的详细错误格式，参考 `templates/error-output.md`（含缺少必填输入/信息不足/字段缺失 3 类示例）。各指令 Prompt 中「输出格式错误返回【格式校验失败】」统一以此为准。

# 人工双盲评测方案

## 定位

前三套自动化脚本（结构校验 / 契约断言 / 记忆端到端 / LLM 端到端）能验证"结构对不对""规则对不对""AI 产出满不满足断言"，但都查不出**"维度分析得对不对""用例设计得合不合理""根因分析有没有逻辑"**——这些是内容质量，需要测试专家人工判定。

本方案定义一套可重复执行的人工评测流程，每版本发布前跑一次，量化 AI 产出的真实可用性。

## 评测频率

| 时机 | 范围 | 耗时 |
|------|------|------|
| 每版本发布前 | 全量 9 条 functional-eval | 约 4.5 小时（2 评审员 × 9 条 × 15 分钟） |
| Prompt 重大改动后 | 改动涉及的指令子集 | 按需 |

## 评测员资质

- **2 名评审员**（双盲：互不知晓对方评分）
- 资深测试工程师（≥3 年测试经验，熟悉被测业务域）
- 评审员不参与被评 prompt 的编写（避免既当运动员又当裁判）

## 评分维度（5 维，每维 1-5 分）

| 维度 | 1 分（差） | 3 分（合格） | 5 分（优秀） |
|------|----------|------------|------------|
| **完整性** | 漏关键维度/场景 | 覆盖主要维度 | 覆盖全部维度+发现隐性需求 |
| **准确性** | 内容有明显错误 | 内容正确 | 内容精准+有依据 |
| **可执行性** | 步骤无法执行 | 步骤可执行但需补充 | 步骤可直接执行 |
| **深度** | 停留在表面 | 有合理分析 | 有洞察+关联历史/规范 |
| **实用性** | 对实际工作无帮助 | 能作为初稿 | 能直接用于工作（仅微调） |

**总分门槛**：
- 单条 eval：平均分 ≥ 3.5 视为合格，< 3.5 需改 prompt
- 版本级：9 条平均分 ≥ 3.8 视为版本达标

## 评测流程

### Step 1：准备（10 分钟）
1. 从 `evals/functional-eval.json` 取 9 条 eval 的 prompt
2. 用 `ci/run_llm_eval.py` 跑一遍，把 AI 产出归档到 `evals/human-review/ai-output-<version>-<日期>.json`（每条 eval 含 id、prompt、ai_output）
3. 打印评分表（模板见下）

### Step 2：独立评分（双盲，每人 2 小时）
1. 两位评审员各自独立阅读 9 条 AI 产出
2. 每条按 5 维度打分（1-5）+ 写评语（≤50 字）
3. **关键**：评审员不得看对方评分，不得看 prompt 源文件，只评 AI 产出本身

### Step 3：校准（30 分钟）
1. 两份评分汇总到 `evals/human-review/score-<version>-<日期>.csv`
2. 计算每位评审员的每条平均分、维度平均分
3. **分歧处理**：同一 eval 两评分差 ≥ 1.5 分的，两人当面讨论达成一致分（记录最终分+讨论要点）

### Step 4：归档与决策（20 分钟）
1. 写版本评测报告（模板见下）到 `evals/human-review/report-<version>-<日期>.md`
2. 决策：
   - 版本平均分 ≥ 3.8 → 准予发布
   - 3.5 ≤ 版本平均分 < 3.8 → 列出低分项，改 prompt 后重评这些项
   - 版本平均分 < 3.5 → 不予发布，全面改 prompt

```markdown
## 维度平均分

| 维度 | 评审员A | 评审员B | 平均 | 最弱项 |
|------|--------|--------|------|--------|
| 完整性 | 4.1 | 4.0 | 4.05 | prd-001（漏维度） |
| 准确性 | 4.3 | 4.2 | 4.25 | — |
| 可执行性 | 3.8 | 3.9 | 3.85 | bug-001（步骤模糊） |

## 分歧处理记录
- prd-001：A=3.6 / B=3.4（差 0.2，无需讨论，取均值 3.5）
- team-001：A=2.8 / B=4.3（差 1.5，讨论后认为风险标注逻辑正确但缺资源调配建议，定 3.5）

## 改进建议（给 prompt 维护者）
1. `prompts/prd/prompt.md`：强化"业务分层维度必输出"约束（已在 LLM 评测中暴露）
2. `prompts/bug/prompt.md`：修复建议需指向具体代码位置/方向（当前过于宽泛）
3. `prompts/report/prompt.md`：阶段报告需补"定性说明"占位符（AI 只能汇总数据，不能判断业务背景）
```

## 与自动化评测的关系

| 评测层 | 查什么 | 发现什么 |
|--------|--------|---------|
| `ci/validate.sh` | 结构 | 文件缺失、版本不一致 |
| `ci/run-evals.sh` | 契约 | prompt 定义与 eval 期望不符 |
| `ci/test-memory-e2e.sh` | 规则 | 记忆模块行为偏离 README |
| `ci/test-memory-stress.sh` | 长期 | 性能退化、重复堆积 |
| `ci/run_llm_eval.py` | LLM 产出 vs 断言 | AI 产出漏维度/字段（结构层） |
| **本方案（人工）** | **内容质量** | **维度分析对不对、用例合不合理、根因有没有逻辑** |

人工评测是金字塔顶端——前面所有自动化层过滤掉结构/规则问题后，人工只评"内容是否真有用"，最大化人工投入价值。

## 落地建议

1. **首次评测**：立即对 v1.5.0 跑一次，建立基线分
2. **纳入发版流程**：在 `docs/version-policy.md` 中加入"发版前必须完成人工评测"的硬门槛
3. **长期追踪**：每版本报告归档到 `evals/human-review/`，绘制版本-分数趋势线，发现 prompt 改进是否真的提升内容质量
4. **评审员轮换**：每 3 个版本轮换一位评审员，避免评分惯性偏差
